# AppGuard 기반 설계

상태: 제안
날짜: 2026-10-20

## 목표
프레임워크에 종속되지 않는 자체 호스팅 가능한 오픈소스 앱 보안 플랫폼을 만든다.
핵심 보안 기능은 AI 모델이나 유료 AI API 없이 동작한다.

## 구성
- Client SDK: 플랫폼 증명, 설치별 키, 요청 보호, 로컬 위험 신호
- Server SDK: 요청 검증, 기존 인증 연계, 정책 집행
- Security Engine: 정책 규격, 검증 결과, 감사 이벤트, 선택형 위협 분석
- Build: 플랫폼별 보호 도구 실행, 매핑 및 심볼 파일 관리
- CLI: 프로젝트 감지, 초기화, 진단, 정책 검증

## 구현 방식
언어별 검증 라이브러리와 공통 규격·테스트 벡터를 채택한다.
각 서버 SDK는 중앙 서비스 없이 기본 검증을 수행할 수 있어야 한다.
중앙 검증 서비스와 공용 네이티브 코어는 운영·배포 복잡성을
평가한 뒤 선택형 확장으로 검토한다.

## 보안 경계
클라이언트와 클라이언트가 보고하는 위험 신호를 신뢰하지 않는다.
앱에 모든 설치가 공유하는 장기 비밀키를 내장하지 않는다.
요청 서명과 앱 증명은 사용자 인증 및 권한 검사를 대체하지 않는다.
난독화와 로컬 탐지는 보조 방어이며 완전한 역공학 차단을 보장하지 않는다.

## 공통 요청 검증 규격
RFC 9421 기반 서명 프로필을 검토하고 지원 범위를 명시한다.
메서드, 대상 URI, 본문 해시, 인증 컨텍스트를 검증에 결합한다.
키 등록, 증명 연결, 갱신, 폐기 절차를 정의한다.
시간 허용 범위, nonce 유효기간, 원자적 재사용 차단을 정의한다.
프록시와 URL 정규화, 본문 변환에 대한 처리 규칙을 정의한다.
지원하지 않는 버전과 알고리즘은 명시적으로 거절한다.

## 독립 사용
Client SDK 없이 서버 인증·인가와 일반 API 보호를 사용할 수 있다.
Server SDK 없이 빌드 보호와 로컬 위험 탐지를 사용할 수 있다.
앱 증명이 필요한 경로에는 별도의 명시적 정책을 적용한다.

## 정책과 운영
Basic, Balanced, Strict를 버전이 있는 정책 프리셋으로 제공한다.
증명 미지원, 검증 실패, 외부 서비스 장애를 구분한다.
허용, 거절, 추가 검증, 관찰의 조건과 사유 코드를 정의한다.
감사 로그에 토큰, 비밀키, 요청 본문을 기본 기록하지 않는다.
보존 기간과 개인정보 최소 수집 기준을 문서화한다.

## 개발 순서
1. 위협 모델, 프로토콜 초안, 정책 규격, 공통 테스트 벡터
2. Spring Boot, Python, Node.js 서버 SDK와 예제
3. Android 및 iOS 증명과 키 관리
4. Unity, Expo/React Native, Flutter 연결
5. 플랫폼별 빌드 보호와 CLI
6. .NET, Go, PHP, 선택형 콘솔 및 AI

## 검증 기준
모든 서버 SDK가 동일한 정상·공격 테스트 벡터를 통과한다.
본문 변경, 만료, 중복 요청, 잘못된 키와 앱 식별자를 검증한다.
동시 요청, 다중 서버, 키 폐기 및 의존 서비스 장애를 검증한다.
모의 증명 테스트와 실제 공급자·기기 검증 결과를 구분한다.
지원 상태는 계획, 구현, 통합 검증, 출시로 구분해 공개한다.

## 이번 단계의 산출물

패키지 배포, 외부 서비스 설정, 제품 구현은 후속 단계로 진행한다.
